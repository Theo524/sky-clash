## Diagnosed reasons earlier iterations missed the player's goal

- `applyAuthoredCruise()` first selects/blends V156 hover→cruise by **forward speed**, then V159–V162 add bone rotations to that existing pose. Limiting `v162UprightVerticalPose` to ~5 degrees only capped the **overlay**, not world-space total lean. The player's feedback and actual Kairo V161/V162 review images showed the silhouettes still looked too similar and too leaned.
- In `tools/capture-flight-video.cjs` with `VISUAL_VERTICAL_QA=1`, both `ascend` and `descend` stages include **`forward:4`**. There is a shorter `vertical-rise` test but **no sustained pure-vertical descent**. This fixture cannot alone demonstrate the upright controlled ascent/descent silhouette requested.
- The same 60-tick gallery captures only **10 ticks for ascent and 10 for descent**. Its thresholds checked numerical `flightVerticalArms`, `flightVerticalLegs`, `flightVerticalFeet` and additional lean; it did not inspect actual full-body world-up posture, silhouette pixel changes, anatomical segment directions or visible stage-specific animation quality. CI green did NOT establish that it looks correct.
- `tools/author-kairo-forward-flight-stills.cjs` was used to author complete true quaternions for **forward** flight, but we didn't reuse it for the new vertical action. The Pose Lab method `authorWorldPose()` authors poses **from key zero**, so a multikey sequence must be explicitly authored/assembled in increasing timestamp order, then reimported and visually checked (rather than treating a set of isolated 2-keyframe stills as a complete motion).
- Pose Lab currently slerps adjacent keys linearly in time; it is a **capable manual keyframe editor**, not a complete production-grade animation graph/easing/IK solution. Runtime V100 still lacks a dedicated authored **ascend/descent multi-keyframe player** and robust transition mixer.
- Some historical full-video workflow assertions pin specific preview versions (`v152,v156` or `v156,v159`); don't assume changing a workflow-dispatch input yields a reusable pass. Make the new keyframe candidate's visual script/verification scenario generic and explicit.
- `docs/ASSISTANT-CURRENT-STATE.md` contained **stale historical V153 release-status** despite `main` boot actually setting `BUILD='V156'`, `flightPreview=v156`. The status document needs the update below; historical blocks must be treated as date-stamped, not authoritative.
